## 1. 为什么最初那样做？

### 先读 [#2852](https://github.com/OpenXiangShan/XiangShan/pull/2852)

2024 年 4 月合并，引入 H 扩展 1.0，改变了 42 个文件。至少看：

- src/main/scala/xiangshan/backend/fu/Fence.scala
- src/main/scala/xiangshan/cache/mmu/TLBStorage.scala
- src/main/scala/xiangshan/cache/mmu/PageTableCache.scala
- src/main/scala/xiangshan/cache/mmu/PageTableWalker.scala
- src/main/scala/xiangshan/cache/mmu/L2TLB.scala

评审中有人指出新增 Guest Physical Address 可能令 IBuffer 面积增加约 50%；讨论回应当时优先处理功能。这是**评审时的估算/担忧**，不是我确认的综合测量结果。

你先画出：CSR/Fence 发令 → TLB 和 PTW Cache 收到控制 → invalidate valid 位 → 在途 refill 如何处理。

### 基础契约：RISC-V 官方规范

- [RISC-V H Extension / HFENCE 文档](https://docs.riscv.org/reference/isa/priv/hypervisor)
- 区分 SFENCE.VMA（当前 S 翻译环境）、HFENCE.VVMA（VS-stage）、HFENCE.GVMA（G-stage）。
- 注意 HFENCE.GVMA 的 rs1 按 GPA 右移 2 位编码；rs2 指定 VMID。允许硬件**过度失效**，不允许漏掉必须失效的 Entry。
- ISA 明确指出：如果 Combined TLB 只缓存 GVA→SPA，要想按 GPA 精确失效，需要额外记录 GPA，代价较大；不少实现选择按 VMID 更大范围失效。

## 2. 为什么中途要改？

### A. 正确性：[#3077](https://github.com/OpenXiangShan/XiangShan/pull/3077)

读 PR 描述，自己写出四种反例：rs1=0 / 非0，rs2=0 / 非0；再加 Global 与非 Global Entry。预测哪些应该被清除，哪些应保留。

**不许直接把“全部 Flush”当作正确性测试的充分条件**；还应检查是否不必要地清掉本可保留的翻译，以分析性能成本。

### B. 性能：[#4390](https://github.com/OpenXiangShan/XiangShan/pull/4390)

老版本的 L2 TLB 部分失效因相关 ASID/VMID/VPN 元数据放在 SRAM 中，难以单周期读全比较，因此保守地清空全部有效项。优化后增加：

- MMUConst.scala: hashAsidWidth = 3, hashVpnWidth = 6（所核验补丁中的默认参数）
- PageTableCache.scala: l0/l1 的 ASID、VMID 和相关 VPN 折叠哈希寄存器
- 以哈希辅助匹配失效条件，降低无关 Entry 被清空的概率

请解释：**哈希碰撞会导致过度失效，还是可能造成漏失效？** 具体答案必须结合补丁的比较/失效逻辑验证，不凭直觉下结论。

性能验证不得只看总 IPC：需比较 Fence 次数、受影响 Entry 数、L2TLB Miss 和 PTW 数量，并检查工作集与切换频率。

### C. 反例：[#5114](https://github.com/OpenXiangShan/XiangShan/pull/5114)

VS-stage 使用大页，G-stage 使用小页；L1 Combined TLB Entry 按较小页表示。此时针对 VS-stage 大页内另一地址执行 HFENCE.VVMA，若只按 Combined Entry 的小页 Tag 匹配就可能**漏失效**。

补丁对相应 L1TLB Fence 路径取消地址过滤，以更大失效范围换取正确性。你要回答：「为什么没有足够元数据就不能既精准又正确？」并写出最小的页号反例。

### D. 最新边界：[Issue #6745](https://github.com/OpenXiangShan/XiangShan/issues/6745) / [PR #6746](https://github.com/OpenXiangShan/XiangShan/pull/6746)

Issue 提供完整复现：
- 先在 S-mode 读 VA 0x40000000，命中物理页 A，数据 0x1111。
- M-mode 修改 PTE 到页 B，数据 0x2222。
- M-mode 设置 MPRV=1、MPV=1、MPP=S，执行 SFENCE.VMA；恢复并在 S-mode 再读。
- 未修复的测试环境可能仍读到 0x1111。控制组不执行 Fence 也读到旧值，但**无 Fence 时不保证每次都返回旧值**。
- 提议：单独携带当前 V（fenceVirt），而不是用 MPRV 影响后的 dvirt 来选择 Fence 目标。

**截至检查日，#6746 仍是 open / unmerged。** 不要把 PR 分支当成主线现行代码，也不要把 #6761（closed/unmerged）当成已合并方案。

## 4. 最小实验：先写软件黄金模型，后读 RTL

输入：{type, rs1, rs2, currentV, dvirt, ASID, VMID, pageSize, gStagePageSize, tlbEntries}。
输出：每个 Entry 是否必须失效（架构要求）与实现是否失效（RTL 行为）。

覆盖测试：
1. SFENCE.VMA：HS/VS 上下文与 rs1/rs2 组合。
2. HFENCE.GVMA：按 GPA、VMID 的失效；含 G-stage 保留 G 位。
3. VS-stage 大页 + G-stage 小页的 Combined TLB 反例。
4. 2026 #6745：currentV=0，dvirt=1，SFENCE 仍应作用于 HS。
5. 性能测试：保守全清 vs 精准清理，对比 Entry 失效数；任何优化不得牺牲架构要求的失效集合。

首期不要求改香山主线代码。若能写出正确 reference model、解释补丁代价并通过独立反例测试，已是高质量交付。
